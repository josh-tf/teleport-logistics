# Relay 0.3.2: hub power visual crash

## Evidence

The supplied `FactoryGame.log` identifies Relay 0.3.1 on Steam build CL502094. At game frame 587, Background Worker #3 hits the renderer's `IsInGameThread() || IsInParallelGameThread()` assertion. The recorded call chain is factory parallel tick → `ARelayHub::ApplyPowerVisual` → `UMaterialInstanceDynamic::SetScalarParameterValue` → `FRendererModule::InvalidatePathTracedOutput`.

This is a Relay threading defect. Successful compilation, cooking and asset inspection did not exercise a live factory worker changing the hub's power state.

## Correction

- Factory ticks now only maintain the hub's power consumption. They never refresh visual state.
- Removed the power-change delegate binding so a callback on a worker cannot reach material updates either.
- BeginPlay initializes client/listen-server visuals and starts an object-bound world timer every 0.1 seconds. The timer reads the latest power state on the game thread. Identical states remain cheap no-ops.
- Dedicated servers create no visual timer or dynamic screen material.
- EndPlay clears the timer before superclass teardown.
- The visual updater has an explicit game-thread check before any cached state, UObject lookup or material operation. This guard also exists in Shipping builds.
- Save properties, building identities, channels, routes and cargo formats are unchanged.

The approach follows [SML factory tick guidance](https://docs.ficsit.app/satisfactory-modding/v3.7.0/Development/Satisfactory/FactoryTick.html) and [Unreal's gameplay timer model](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-timers-in-unreal-engine).

## Regression coverage

`Relay.PowerVisual.RejectFactoryWorkerUpdates` calls the actual native visual updater 512 times on an Unreal thread-pool worker. It checks that visual caches, material references and mesh overrides remain untouched. Source checks additionally reject a direct visual call in the hub factory tick or restoration of the unsafe power delegate.

The native test passed in the CSS Unreal Linux editor: one succeeded, zero failed, zero warnings and zero errors. The exported result is [0.3.2-automation.json](0.3.2-automation.json). The editor was launched with `-TestExit="Automation Test Queue Empty"`; that log-triggered forced shutdown returned process code 1 after the successful test/report export. Test acceptance is taken from the structured automation result, not that shutdown code.

The clean `WindowsAll` pipeline completed with exit code 0. Linux `FactoryEditor` and all three Win64 Shipping modules (Steam, Epic, dedicated server) compiled and linked successfully. Asset import and class-default inspection both completed with zero errors; Windows and WindowsServer each retained 25 packages. The client IoStore has 40 chunks; the server has 26. Both platform archives carry manifest version 0.3.2 (numeric version 6). The release assembler validates archive CRCs, manifest versions, required DLLs, IoStore files and platform layout, and emits SHA-256 checksums.

## In-game acceptance

Replace Relay 0.3.1 with 0.3.2 with the game closed, then reload the save that crashed. Check an existing hub without power, connect/disconnect its power repeatedly, and check its lights and screen. Save/reload and repeat with a joining client. The expected visual response is within about 0.1 seconds of the locally observed power change. A full live-game retest remains required; headless automation does not establish renderer appearance or replication latency.
