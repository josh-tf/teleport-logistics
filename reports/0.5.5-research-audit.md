# Research and startup audit — Relay 0.5.5

## Findings

**0.5.4 introduced an object-lifetime defect.** It installed runtime-created Blueprint unlock objects into native schematic CDOs without an independent GC reference. A native CDO can be excluded from GC traversal. The latest retail stack fails in SML's `AutoRegisterUnlockReferences`, consistent with reading a collected unlock. Version 0.5.5 pins the two objects with `TStrongObjectPtr`. The new regression removes both reflected CDO edges before collection and proves the objects remain alive.

**The 0.5.1 constructor loading remains an inferred trigger, not a proven corruption mechanism.** Both 0.5.1/0.5.2 failed during native Build Gun construction; disabling Relay allows a fresh world to load. 0.5.4 proceeds past Build Gun construction and fails later in schematic registration. Deferred Blueprint loading is retained; no assertion is bypassed and no Build Gun construction data is modified.

**Earlier inspections were incomplete.** Counting rewards and checking their Blueprint interface immediately after creation did not establish lifetime safety. The SDK also has a stub `UFGBuildingDescriptor::GetBuildableClass` that always returns empty. The expanded inspection reads the stored property instead. These constraints were missed in earlier acceptance claims.

## Registration and lifecycle review

- Both schematic classes remain in the root `URelayWorldModule::mSchematics` array. SML registers these during world INITIALIZATION, recursively registering their recipe and descriptor references.
- Native constructors create native default unlock subobjects only. Game-instance INITIALIZATION prepares the stock reward presentation before world registration consumes it.
- Replacement objects retain their recipe arrays and are referenced by the reflected schematic array plus explicit lifetime guards. The guards are process-lifetime state with only two entries in the normal initialization path.
- Repeated initialization preserves identity and does not duplicate rewards. If the stock class or reflected fields cannot be resolved, native recipe unlocks remain; the UI presentation may be absent, but an error is logged.
- Unlocking still uses the stock `UFGUnlockRecipe` implementation. No custom purchase RPC, grant-on-load or save migration was introduced.
- Existing schematic, recipe and building class paths remain unchanged. This supports save compatibility by design, but actual purchase/reload acceptance is pending.
- The map hook carrier already has a strong lifetime reference; the sign-icon textures and Personnel widget resources use reflected retained properties. This review found no analogous missing retention there. This is source review, not complete retail acceptance of those features.

All four logistics endpoints cost 4 Reinforced Iron Plates, 4 Circuit Boards and 10 Cable to build. The logistics hub adds 5 Computers. Personnel construction costs 20 Time Crystals, 10 Supercomputers and 5 Turbo Motors.

The inspection verifies exact resource class identities and quantities, one product per recipe, each product's intended descriptor/building, a hologram class for every building, category/subcategory placement, stock reward interface and icon assets. These are HUB milestones, not MAM research nodes. Tier placement is retained; no new inter-milestone dependency was added.

## Verification results

- Eight native automation tests passed: seven clean and one existing test with reconstructed SDK Blueprint warnings. Zero failures. Report: `0.5.5-automation.json`.
- New `Relay.Research.RewardLifetime` test removes CDO references, forces full collection, restores references and repeats initialization/collection three times while checking identity and reward counts.
- Fresh Unreal content inspection passed, including exact resource/product/hologram checks and deferred reward interface checks after collection.
- Transport/model/source checks passed, including 60,000 randomized item-conservation steps under AddressSanitizer/UndefinedBehaviorSanitizer.
- Linux editor build and Windows Steam/Epic/server packaging passed. Final package validation is recorded in the release checksums.

## Still requires retail-game verification

Fresh-map loading; loading an existing save; the actual HUB reward widgets; paying both milestones and receiving all recipes; saving/reloading purchased milestones; multiplayer clients receiving the same unlocked recipes. The reconstructed SDK cannot prove these game implementations. No claim that the retail crash is fixed is made before this check.
