# Pre-publication review: TeleportLogistics 0.5.10

## Verdict

Not publishable as-is. The transport core, the redirect table and the save/net flag audit all came back clean, and every advertised number in the docs matches the code, so the engineering is in release shape. The publication surface is not. The `Teleporter -> TeleportLogistics` find-and-replace ran over prose it should not have touched, and the damage landed in the five artifacts that go public first: the store showcase banner still reads `TELEPORTER` (a name owned by a different 333k-download SMR mod), the README names two HUB milestones that do not exist, the publication kit declares the chosen SMR reference both taken and free three lines apart, the store description carries a mangled wiki URL, and the clean-room guard plus the provenance statement were both mangled by the same find-and-replace. Separately, the repo cannot be pushed as it stands: 1,676 tracked `node_modules` files including a 10.3 MB prebuilt Linux `esbuild` (present at two paths, so 20.6 MB of tree) sit in history from the root commit, and there is no LICENSE file for source the listing already links to three times. Twelve blockers, all of them cheap except the license decision and the history rewrite.

## Bugs

### Native transport core

**`TeleportLogisticsBuilding.cpp:366` (PLAUSIBLE, medium, maintainer decision).** Fluid intake never consults the route's locked fluid. Line 366 is `Type = Cargo.IsEmpty() ? Pipe->GetFluidDescriptor() : Cargo[0].Item.GetItemClass();` and the pull follows at 371-378. `Route.Fluid` appears only at `TeleportLogisticsSubsystem.cpp:182,194,322`, all in the scheduler's move adapter, which refuses the transfer after the wrong fluid is already in the buffer. Once `Cargo` is non-empty, line 366 pins `Type` to the wrong fluid and keeps pulling it. Why it matters: the endpoint then cannot be dismantled (`Building.cpp:444` requires `Cargo.IsEmpty()`), rerouted (`Subsystem.cpp:245`) or reset (`Subsystem.cpp:318-321`), and the locked fluid type is invisible to the player because `FTeleportLogisticsRoute::Fluid` (`Types.h:37`) is `UPROPERTY(SaveGame)` with no `BlueprintReadOnly` and is never rendered in `TeleportLogisticsWidget.cpp`. Not a trap: `docs/design.md:18` specifies disable, flush, reset as the designed recovery, so the exit costs one 50 m3 buffer. Fix: resolve the route at intake and treat a locked mismatch as no intake, so the pipe backs up visibly instead of the endpoint stalling. The mutex is already shared between both sides. Independently, render `Route.Fluid` next to the buffer readout at `TeleportLogisticsWidget.cpp:478-482`; the field is already in the snapshot.

**`TeleportLogisticsSubsystem.cpp:31-45`, `:290-294` (from the missed notes, two domains, needs a maintainer answer).** Duplicate-GUID remap orphans routes permanently. `Register` reassigns `Building->TeleporterId = FGuid::NewGuid()` on a collision and, for a hub, adds a fresh channel keyed on the new GUID. Existing routes keep `Channel` pointing at the old hub GUID, and `Control` at 290-294 only matches `Route.Channel == Hub->TeleporterId || !Route.Channel.IsValid()`, so those routes can never be renamed, paused or deleted by any hub. `Snapshot:343` drops the stale channel record and `:381` renders the routes under "Default". The 256-route cap at `:249` counts them regardless of reachability. Trigger is rare (duplicated saves, copied blueprints) and neither the migration test nor the audit covers a saved identity collision. This is the one path in the save domain that can silently mangle saved routing state.

**`TeleportLogisticsSubsystem.cpp:159` and `Core/TeleportLogisticsScheduler.h:37` (CONFIRMED, low).** The header asserts "stalled ports never consume credit"; the code destroys their credit. Lines 158-159 substitute `teleport_logistics::Budget{}` for a stalled input, 166-167 for a full output, and the write-back at 209-214 copies that zero onto the live endpoint with no participation test. Masked in steady state because accrue caps at 5 items / 2500 units and a 20 Hz tick re-accrues 1 item / 500 units, so the documented 1,200 items/min and 600 m3/min ceilings hold. The visible effect is that the quarter-second burst reserve promised at `docs/design.md:25` is discarded every tick a port is empty or full, so recovery after a hitch is slower and uneven. Fix: guard the write-back with the same predicate used for the snapshot, or stop substituting `Budget{}` at all since the move adapter already returns 0 for stalled ports. If the zeroing is deliberate, correct the header comment.

**`TeleportLogisticsSubsystem.cpp:57` (CONFIRMED, low).** `FRouteRuntime` entries leak on hub dismantle. `Unregister` does `Routes.RemoveAll(... R.Channel == Building->TeleporterId)` with no `Index` cleanup, while the explicit delete path at 331-332 pairs `Routes.RemoveAll` with `Index.Remove(Id)`. `Index.` appears at exactly three sites (75, 147, 332), and `Reindex` only resets existing entries, so an orphan with two empty `TArray`s and two empty `std::vector`s survives every rebuild. Tens of bytes per build/dismantle cycle, no save impact. Fix: hoist a "drop `Index` keys with no surviving Route" sweep into `Reindex`, which already iterates the map, and delete the special case at 332.

**`TeleportLogisticsBuilding.cpp:494-498` against `TeleportLogisticsSubsystem.cpp:225-226` and `:327-330` (from the missed notes, needs a maintainer answer).** The two definitions of "empty" disagree. Hub dismantle gates on `ChannelEmpty`, which counts only endpoints where `E->DirectoryActive()`, and `DirectoryActive` (`Building.h:37`) is false for anything `IsAboutToBeDismantled()`. Route deletion uses the stricter test and refuses while any endpoint references the route, active or not. So a hub can be dismantled while endpoints pending dismantle still reference its routes, and `Unregister:57` then removes them. If those endpoint dismantles do not go through, they hold a `RouteId` that resolves to nothing: `RefreshMap:109` labels them "Unassigned", `Tick:145-147` never iterates them, and any cargo is frozen until the player disables and flushes. Whether the engine can leave a partially cancelled dismantle selection is the open question. If it can, the fix is to make `ChannelEmpty` use the same predicate as the delete path.

### Save, redirects and multiplayer

**`TeleportLogisticsSubsystem.cpp:342-344` (CONFIRMED, medium).** The snapshot RPC pages `Endpoints` (clamped to 64 at 395-397) but ships `S.Channels = Channels;` and `S.Routes = Routes;` whole on every poll. Routes are capped at 256 (`:249`); Channels are uncapped, one per hub, added at `:44` with only a duplicate-Id guard. Transport is `UFUNCTION(Client, Reliable)` (`RemoteCall.h:35`, invoked at `RemoteCall.cpp:113`) and the widget re-polls every 0.9 s, or 0.30 s while a mutation is pending (`Widget.cpp:816`). The unpowered-hub branch (`RemoteCall.cpp:95-98`) resets `Endpoints` but still ships the full arrays. Why it matters: tens of KB of reliable traffic per second per viewing player at the documented ceiling, with no bounded worst case on the Channels side. Fix: page both arrays the way `Endpoints` is paged, or at minimum give `Channels` the same explicit cap. Do not use `MutationRevision` as a staleness gate: it is only populated when `MessageContext == Context->TeleporterId` (`RemoteCall.cpp:100-103`), so it is the calling player's own mutation counter, and the widget uses it to detect its own pending action completing (`Widget.cpp:828`). A separate data revision bumped where `Dirty`/`MapDirty` are set would be needed.

**`docs/migration/README.md` (from the missed notes, medium, needs a maintainer decision).** The duplicate-module hazard is documented and not enforced. The doc tells the player "Do not enable both modules: they would register two sets of buildings and subsystems", and nothing in `TeleportLogisticsContent.cpp` or the world module detects a co-installed legacy `Relay` or `Teleporter` module. Old internal builds exist in testers' hands, so this is the most likely save-damage report on a first release, and it rests on a README step. A one-line check for the legacy module at startup, logging and refusing to register, would close it.

**`TeleportLogisticsSubsystem.cpp:364-366` and `:399` (from the missed notes, low).** The synthetic `Default` channel is inserted after the dead-hub filter (`S.Channels.Insert(Default, 0)`) and then counted by the status line `Network online · %d channels · %d routes`, so the channel count the player sees is always one higher than the hubs that exist. Subtract one, or count before the insert.

**`TeleportLogistics/Config/DefaultTeleportLogistics.ini:55` and `:177` (PLAUSIBLE, low, maintainer decision).** Two redirect entries are most likely unreachable. Line 55 is keyed on `/Script/Teleporter.TeleporterBuilding.RelayId`, and the interim build declared `TeleporterId` (`.toolchains/legacy-teleporter-stage-0510/Source/Teleporter/Public/TeleporterBuilding.h:95`), never `RelayId`; the interim config carried the same entry, so it was deliberate coverage for a resolution-order question rather than copy-paste. Line 177 carries `ValueChanges=(("RelayRecipes","TeleporterRecipes"))` on the Teleporter-keyed `TeleporterUnlock` redirect, but the interim build already created the subobject as `TeleporterRecipes` (`legacy-teleporter-stage-0510/.../TeleporterContent.cpp:158`), so that clause is inert while the identical one at `:38` is live. Nothing in the suite exercises either: `TeleportLogisticsMigrationTest.cpp:152-155` asserts the interim `TeleporterId` path only, and no test touches `ValueChanges` at all. Safer half of the fix: leave both entries, move :55 under the Teleporter section header at :144 where its key belongs, and correct the 134/131 split at `reports/0.5.10-release-audit.md:27`.

### Build and release integrity

**`scripts/build-linux.sh:43` and `scripts/build.ps1:23-27` (PLAUSIBLE, low, maintainer decision).** The legacy co-discovery guard tests `-f "$project_root/Mods/$legacy/$legacy.uplugin"`, so it matches only when the directory name matches the `.uplugin` name, while the comment at `build-linux.sh:41` states the invariant as "do not discover both old and new native modules". `mv Mods/Relay Mods/legacy-relay-stage-0510` satisfies the guard and leaves `Relay.uplugin` in the tree. **`scripts/package-release.py:62-64` (CONFIRMED, low).** The packaged side is decoded `utf-8-sig`, the source side with `read_text()`'s plain utf-8 default. `directives()` (35-41) strips only whitespace and `;` comments, so a BOM on `TeleportLogistics/Config/DefaultTeleportLogistics.ini` (any Windows editor adds one, and `build.ps1` is the alternate build path) survives into the first element and aborts the release with "packaged compatibility redirects differ from source" over three invisible bytes.
